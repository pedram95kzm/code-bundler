# Technical Design

## Module map

| File | Key types/functions | Notes |
| --- | --- | --- |
| `src/main.rs` | `main`, `application_icon` | Executable entry point and embedded assets. |
| `src/app.rs` | `CodeBundlerApp`, `Mode`, `Message`, `update`, `view` | Elm-style application state and rendering. |
| `src/workflow.rs` | `GenerationReport`, `generate_project` | Coordinates paired outputs and prompt streaming. |
| `src/extractor.rs` | `ExtractionReport`, `extract_folder_to` | Scans a folder and writes the bundle. |
| `src/embedder.rs` | `EmbedReport`, `embed_file`, change parsers | Restores bundle entries and applies content/file changes. |
| `src/paths.rs` | Portable path functions | Shared path validation and case-insensitive keys. |
| `src/compression/mod.rs` | `safely_compress` | Extension router. |
| `src/compression/brace.rs` | State-machine compactor | Brace-style languages, strings, comments, raw strings. |
| `src/compression/python.rs` | State-machine compactor | Python indentation, comments, quoted/triple-quoted text. |

## UI state and events

`CodeBundlerApp` stores only transient process state:

- selected mode;
- typed project, bundle, and modification paths;
- optional request text;
- compression toggle;
- current notice;
- `busy` guard.

`update` ignores editing/action messages that arrive while `busy` is true.
Browse operations and file workflows are represented as Iced tasks. The Cargo
feature set includes `thread-pool`; filesystem functions themselves are
synchronous and contain no internal `await` points.

## Bundle format v1

The format is UTF-8 text generated by the application:

```text
==code-bundler:v1==
==relative/path.ext content==
==utf8-bytes:N==
<exactly N UTF-8 bytes of content>
<one entry-separator newline>
```

For skipped data, the metadata line is replaced by:

```text
[Skipped: binary file]
```

The next blank line is ignored by the parser. The length is measured after
optional decoding and compression. It lets the parser distinguish content from
header-like text and preserve empty files and final newlines.

Only `==code-bundler:v1==` is accepted. The parser performs checked length
addition, verifies bounds and UTF-8 character boundaries, and requires a
newline separator unless content ends exactly at end-of-document.

## Text classification and decoding

1. A NUL in the first 8,192 bytes classifies data as binary unless it begins
   with a UTF-16 LE/BE BOM.
2. UTF-32 BOMs are rejected.
3. BOM-marked UTF-16 must contain an even number of bytes and valid surrogate sequences.
4. UTF-8 accepts an optional BOM and otherwise must be valid.
5. Failed decoding is emitted as a binary skip marker during generation.
6. A selected bundle or modification file that fails decoding is rejected.

UTF-16 source encoding is not preserved; decoded content is serialized as UTF-8.

## Project discovery

`ignore::WalkBuilder` is configured with:

- hidden filtering off;
- parent rules off;
- `.ignore`, global Git, and `.git/info/exclude` rules off;
- `.gitignore` rules on without requiring a Git repository;
- symbolic-link following off;
- an entry filter for VCS metadata names.

Each discovered file is converted to a portable `/`-separated relative path.
The complete set is validated for case-only duplicates and file/parent
conflicts before the output file is created.

## Portable path algorithm

Every component must be normal, non-empty Unicode and must not:

- be `.` or `..`;
- end in a dot or space;
- contain a control character or `< > : " \\ | ? *`;
- have a case-insensitive basename equal to `CON`, `PRN`, `AUX`, `NUL`,
  `COM1`–`COM9`, `LPT1`–`LPT9`, `CONIN$`, or `CONOUT$`.

Lowercased component keys are used for matching and collision checks.

## Output naming

Generation sanitizes the selected folder's final component:

- alphanumeric, `-`, and `_` are retained;
- each run of other characters becomes `_`;
- leading/trailing `_` is removed;
- an empty or unavailable name becomes `project`.

It then selects the first pair where neither output exists:

```text
extracted_content_<project>[_N].txt
generated_prompt_<project>[_N].txt
```

Restore uses the bundle stem and atomically claims the first available
`<stem>_embedded[_N]` directory with `create_dir`.

## Prompt assembly

`sample_prompt.txt` is compiled into the executable with `include_str!`.
Generation splits it once around each required placeholder, opens the completed
bundle, and uses buffered writes plus `io::copy`. The request is trimmed at both
ends. A template change therefore requires rebuilding the executable.

## Compression algorithms

The brace-style state machine collapses whitespace outside literals/comments
to a single separator. It retains line-comment endings, quoted content,
backslash escapes, Rust hash-delimited raw strings, and block comments. On a
PHP heredoc/nowdoc candidate or C++ raw-string candidate, it conservatively
copies the remaining input unchanged.

The Python state machine preserves leading indentation on nonblank lines,
physical newlines for content/comment lines, quoted and triple-quoted content,
and comment text. It removes blank physical lines outside multiline strings and
collapses non-leading whitespace runs.

Neither algorithm parses an abstract syntax tree or invokes a compiler.

## Change-file grammar and algorithm

Record prefixes and field names are exact and case-sensitive:

```text
file:<portable-path>,line:<positive-usize>,new_content:<text>
add_file:<new-portable-path>,new_content:<text>
delete_file:<original-portable-path>
rename_file:<original-portable-path>,new_path:<new-portable-path>
```

Before the first record, blank lines and lines whose trimmed form starts with
`#` are ignored. After a replacement or add record begins, non-record lines are
appended to its content with `\n`. A complete subsequent record ends that
multiline content. Structural records do not accept continuation content. While
a content record is open, a continuation line beginning with `\` is unescaped
by removing that first character. This lets `\delete_file:literal`, for example,
produce the literal content line `delete_file:literal`; an actual leading
backslash is encoded with two leading backslashes.

Application steps:

1. Build a case-insensitive map from original bundled paths to entry indexes.
2. Reject missing delete/rename sources, multiple structural operations on one
   source, duplicate additions, and modification-plus-delete conflicts.
3. Group line replacements by original entry and reject duplicate `(file, line)` targets.
4. Decode each edited entry as UTF-8, validate original line spans, sort targets
   descending, normalize line endings, and replace the line content spans.
5. Remove deleted entries, update renamed paths simultaneously, and append added
   entries with their complete UTF-8 content.
6. Revalidate the complete final tree for case-insensitive duplicates and
   file/parent conflicts.
7. Only after all validation succeeds, claim and write the output directory.

Because structural sources refer to the original tree, line edits can target a
file that is renamed in the same change set. Rename swaps and destinations
vacated by another structural operation are valid when the resulting final tree
is conflict-free.

## Error handling and cleanup

- Public workflow functions use `Result<Report, String>`.
- The GUI displays error strings without a separate error code.
- A generated bundle is deleted if paired prompt creation fails.
- A partially written prompt is deleted when possible.
- A partially written bundle is deleted when possible.
- Restore write errors identify the incomplete output directory rather than recursively deleting it.
- Source read failures are accumulated as warnings and do not fail generation.

## Concurrency, retries, caches, and events

- One user operation is allowed at a time by the `busy` flag.
- Iced schedules tasks; core file processing is sequential.
- There are no retries, caches, queues, domain events, background daemons, or scheduled jobs.

## Configuration and observability

- User-visible behavior is configured only through paths, request text, mode, and compression toggle.
- Build configuration lives in Cargo files, `build.rs`, and the CI workflow.
- There are no runtime environment variables, config files, log sinks, metrics, or traces.
